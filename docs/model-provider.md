# Optional model proposal adapter

`web/model-planner.js` exports `proposePlan({ endpoint, model, apiKey = '', prompt, sourceContext, sourceContexts, evidenceBundle, observationBundle, history = [], signal, fetchImpl = fetch, timeoutMs = 60000 })`. It makes one explicit browser request and returns `{ proposal, audit }`. It never executes tools, retries, loads measurements, or changes application state. Reviewed callers present a proposed plan before explicit execution; the separately authorized autonomous controller may execute validated plans within its bounds.

Provide the full Chat Completions endpoint, using HTTPS or HTTP on `localhost`, IPv4 loopback, or `::1`. URL credentials, query strings and fragments are rejected. Requests use POST, `credentials: 'omit'`, `redirect: 'error'`, `cache: 'no-store'`, and `referrerPolicy: 'no-referrer'`. An optional key is sent only as a Bearer header, never saved by this module. Browser CORS rules still apply. Provider compatibility and availability are not assumed; no live provider test is included.

## Transmitted context

Use `sourceContext` for one channel, or mutually exclusive `sourceContexts` for 1–8 explicitly selected channels. Duplicate tuples and conflicting hashes for one filename reject. Each context requires `file`, `source_sha256`, and `channel`. Optional fields are `title` (255 characters), `warnings` (up to 32 strings of 1,000 characters), `units: { xy_unit, z_unit }`, and `geometry: { shape, xreal, yreal, xoff, yoff, xy_unit, z_unit }`. Geometry is complete when supplied: shape is exactly two positive integers `[height, width]`, extents are positive finite numbers, offsets finite, and units strings or null. Supplied units must agree with geometry. Raster arrays, full instrument metadata and other keys are rejected. Titles and warnings are explicitly marked as untrusted data in the model instructions.

The prompt is limited to 8,000 characters. Optional history is capped at 12 strict `{ role, content }` messages, with roles `user` or `assistant`, 8,000 characters per message and 16,000 total. History follows the system instructions and precedes the current request. Callers should provide only prior user prompts and validated proposal text, never numerical result arrays, and reset history when the selected source set or evidence selection changes. The request includes the actual typed tool catalog, plan constraints and curated context. The serialized request is capped at 256 KiB UTF-8 before network dispatch. It requests `response_format: { type: 'json_object' }`, `stream: false`, and `store: false`, following the [Chat Completions API](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create). JSON mode does **not** guarantee schema adherence; local schema validation remains mandatory, as described in the [structured outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat). `store: false` is a request option, not a claim about arbitrary providers' retention policies.

## Optional verified evidence

`evidenceBundle` is local input with exactly `{manifest,journal,step_ids}`. Select 1–4 completed surface analysis/replay steps. The adapter verifies the bundle using `createEvidenceReport`, binds the recorded source and any reference to selected tuples, and projects at most 32 claims. The bundle itself never enters the request. Only claim IDs, exact recorded values/units/definitions, source/channel identities, artifact IDs, plan/journal hashes, run status and selected-step warnings are transmitted. No recipes, profiles, rasters, full artifacts, journals or Markdown reports are transmitted. The projection is capped at 64 KiB UTF-8; excess data rejects instead of silently dropping warnings.

Warnings come only from selected verified results, including support and unknown-unit warnings. Unselected steps' warnings and error messages are excluded; incomplete runs receive a generic notice. Integrity checking is not independent numerical re-analysis, author authentication or calibration certification.

An evidence response contains 1–32 unique IDs from the exact transmitted claim set. Unknown IDs, additional values/free-form conclusions and evidence responses without opt-in reject. The browser renders the corresponding recorded values and artifact links itself, labeled as model-selected evidence. This does not modify a plan or run tools. It does not assert confidence intervals, independent samples or scientific interpretation.

## Optional verified observations

`observationBundle` accepts exactly `{manifest,journal,step_ids}` alongside an optional `evidenceBundle`. It selects 1–16 completed `check_quality`, `segment_surface`, `measure_texture` or `analyze_sensitivity` steps. The adapter snapshots inputs before awaiting verification and calls `createModelObservations`; only the resulting `observationsContext` enters the provider payload and audit. The local bundle never leaves the browser. Each observation identifies its step, tool, artifact and exact source tuple, with a typed summary and relevant warnings. Plan/journal hashes establish attribution.

Source and reference tuples must be selected and agree with the verified call. Recipe-based tools must match the exact earlier analysis/replay recipe artifact within that plan, including normalized parameters. Surface claims remain independently available. Observations retain units, definitions, calibration/model assumptions, and failed sensitivity alternatives; they exclude bulk rasters, profiles, region tables, recipes, unrelated warnings and free-form failure exceptions. The projection is limited to 64 KiB UTF-8; the entire request still has the combined 256 KiB limit. Neither bound silently truncates required results or warnings. See [verified tool observations](model-observations-design.md).

With supplied observations, the model may return exactly `{kind:"observations",observation_ids:[...]}` containing 1–16 distinct known IDs. No additional values or conclusions are accepted. The audit status is `observations` and `proposal_plan_sha256` is null. Observation artifact IDs do not authorize cross-plan references. These are recorded summaries, not new measurements, confidence intervals, calibration certificates or defect identities. Requests without observation input retain their existing payload/audit fields.

Autonomous next rounds receive this context automatically from the latest eligible run, including quality-only runs, and may terminate as `observations_returned`. The reviewed UI continues to offer explicit surface-evidence selection only; `observationBundle` is available to adapter callers, not a new reviewed-UI selection control.

## Validation and audit

Accepted responses are `{ kind: 'plan', plan }`, `{ kind: 'clarification', question }`, `{kind: 'evidence', claim_ids}` when verified evidence was supplied, or `{kind: 'observations', observation_ids}` when verified observations were supplied. Plans pass `validatePlan`, remain limited to 16 steps, and must bind every supplied file/hash/channel combination to one selected tuple. Reference tuples must be selected; quality reference channels must belong to the same selected file/hash. Matching different identity fields to different sources rejects. Artifact arguments must reference earlier steps through `$step:ID`; raw artifact IDs are rejected. Clarification questions are limited to 2,000 characters. Refusals, incomplete completions, malformed JSON, invalid plans and API-key reflection are rejected.

Response bytes are read incrementally and capped at 1 MiB. Timeout and external cancellation cover both fetch and body reads, including providers that ignore abort signals. Failed requests return `proposal: null` with a generic audit error; local configuration errors may throw a sanitized message before fetching. Audit status is `proposed`, `clarification`, `evidence`, `failed`, or `canceled`; it includes protocol, endpoint, model identifiers when available, timestamps, request-body SHA-256, the exact credential-free request body (including messages), curated context and validated proposal. A configured API key occurring anywhere in the request body, endpoint or model causes local rejection before fetching. Headers, API keys, raw provider responses and provider error text are excluded. For validated plans, `audit.proposal_plan_sha256` hashes the UTF-8 `JSON.stringify(proposal.plan)` text exactly as `runPlan` computes its manifest `plan_sha256`. The hashes match only if the reviewed draft remains unchanged; edits produce a different execution hash. Evidence, clarification and failed/canceled requests record null. Audit provenance records what was proposed; it does not certify scientific correctness.

## Browser workflow

Start the supplied server with `AFM_MODEL_ORIGIN=https://your-provider.example npm run dev` (HTTP is permitted for localhost/127.0.0.1/::1). Its CSP permits that exact origin, and `GET /__afm_config.json` exposes the non-secret setting. For several providers, use a comma-separated list, for example `AFM_MODEL_ORIGINS=https://api.openai.com,https://api.groq.com npm run dev`. Both variables can be combined; duplicate origins are removed. The configuration also exposes `model_origins`. With both variables unset, model requests are disabled. Other static hosts must configure their own CSP; the provider must support browser CORS.

In Assistant, refresh loaded sources, select a channel, expand **Ask for a plan**, and enter the full endpoint, model and optional key. Sending a message requests a proposal only. Use **Add current channel** to build an explicit source selection; without a list, the current inspected channel is used. After verifying a local evidence report, optionally select up to four result steps. Follow-up messages include bounded prior user messages and validated responses; changing selected sources or evidence resets conversation context. Review the proposed plan below, validate, and explicitly run it. Only explicitly selected verified compact claims can be sent; other numerical results remain local. Download the conversation audit separately from the tool journal; matching `proposal_plan_sha256` and run `plan_sha256` link an unchanged proposal to execution.

The UI retains at most 16 request audits, with the current conversation bounded to 12 messages/16,000 characters. Older complete exchanges may drop from model context; full request audits remain downloadable until reload. **New conversation** clears context without erasing audits; **Clear credential** clears the key field. Nothing is saved to localStorage.

`tests/browser-model.mjs` exercises clarification history, explicit execution, proposal/run identity, reflected-key rejection, cancellation and mobile layout using intercepted responses. Start a QA server with `PORT=4176 AFM_MODEL_ORIGIN=https://provider.example node scripts/serve.mjs`; use the existing Playwright environment variables documented for browser tests. No real model/provider has been contacted or certified.

## Autonomous and help modes

The shared connection now includes [provider presets](provider-compatibility.md) and a custom full completion URL. Session-only keys and the exact host-origin gate apply to reviewed planning, [autonomous analysis](autonomous-agent.md) and the separate [help agent](help-agent.md). The toolbar **Documentation** link opens the guide and pilot SOPs without requiring a provider.

`proposePlan` accepts optional `mode: 'reviewed' | 'autonomous'` (reviewed default). Autonomous instructions reflect the user's bounded execution authorization; schema/source/evidence gates remain identical. Optional `onAudit(snapshot)` receives detached credential-free request provenance before dispatch and the final audit, enabling cancellation records in the goal controller. The adapter itself still executes no tools.

## Dashboard guide

Open **Agent** in the header for planning and running analyses beside the maps and measurements. Open **Guide** for interface help and workflow explanations; it cannot execute analysis tools. Switching views preserves both conversations and any running goal. On smaller screens it appears below the workspace. Connection settings are shared by the help, reviewed-plan and autonomous modes. The required goal field comes before the optional SOP; the advanced JSON settings are optional record-checking inputs.

Autonomous activity lists each round, proposed tool, rationale and execution status. Completed surface steps display recorded Sa/Sq and offer **Show on dashboard**. This action strictly replays the chosen recipe locally before displaying it; running a goal does not automatically replace the viewer. Detailed JSON and downloaded audits remain available. Provider compatibility tests use mocked responses, not live-provider certification.
